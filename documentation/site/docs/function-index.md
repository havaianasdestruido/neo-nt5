Everything under `reference/` is generated by
[`documentation/scripts/generate.py`](https://github.com/havaianasdestruido/neo-nt5/blob/main/documentation/scripts/generate.py)
from the tracked files in this repository. It is a **syntactic inventory**: a list of definitions,
their signatures as written, and where they are called in test-named files. It is not proof of
behaviour, coverage or equivalence.

## What the generator does

```text
git ls-files --cached --others --exclude-standard
        |  keep .c .h .cpp .cxx .cc .hpp .hxx .py
        v
tree-sitter (C grammar for .c, C++ grammar for headers/C++)  +  Python ast
        |  function_definition nodes  ->  name, line, signature, sha256(body)
        |  call_expression nodes      ->  only in test-named paths
        v
SQLite (temporary) -> bucket by top-level tree -> pages of <= 300 entries
        v
reference/index.md, reference/<tree>-NNNN.md, reference/coverage.md
```

The extension map is explicit:

```python
EXTENSIONS = {'.c': 'c', '.h': 'cpp', '.cpp': 'cpp', '.cxx': 'cpp',
              '.cc': 'cpp', '.hpp': 'cpp', '.hxx': 'cpp', '.py': 'python'}
```

Headers are parsed with the **C++** grammar, which is why some C headers report parse errors. The
toolchain is pinned in `documentation/requirements.txt`:

```text
tree-sitter==0.25.2
tree-sitter-c==0.24.1
tree-sitter-cpp==0.23.4
```

Scale in this checkout: **120,323** tracked files match those extensions, out of 277,956 tracked
files overall. A prefix-limited run over just `base/ntos/se/` scans 57 files and extracts 401
definitions with 40 partial parses — a useful sense of the parse-error rate in dense legacy C.

## The three kinds of page

| Page | `sidebar_position` | Contents |
| --- | --- | --- |
| `reference/index.md` | 90 | Run summary, totals, links to every bucket page |
| `reference/<tree>-NNNN.md` | 91 | Up to 300 entries for one top-level tree |
| `reference/coverage.md` | 92 | Files with parse errors and files that could not be parsed |

Filenames are stable for a given tree and ordering, so `base-0001` is the first page of the `base`
tree on every regeneration. The hand-written guide pages occupy positions 1–11, which keeps the two
kinds of page in separate groups in the sidebar.

Generated pages are **not committed**. `documentation/.gitignore` excludes `site/docs/reference/`,
and the generator deletes the Markdown files in its output directory before writing:

```python
# No stale pages on a regeneration. Only remove our own generated Markdown.
for old in output.glob('*.md'):
    old.unlink()
```

## Anatomy of an entry

A real entry, from a run over `base/ntos/se/`:

```markdown
## ` SepDumpToken `

- Source: [` base/ntos/se/token.c `:1862](https://github.com/.../base/ntos/se/token.c#L1862)
- Signature: ` VOID SepDumpToken( IN PTOKEN T ) `
- Implementation: inspect the linked definition and body; this index does not infer runtime behavior.
- Variants: No other extracted definition with this exact name.
- Test evidence: No matching call found in test-named files.
```

Each line means exactly what it says, and no more:

- **Source** — the path and line of the `function_definition` node, linked at the run's revision.
- **Signature** — the text from the start of the definition to the opening brace of the body,
  whitespace-collapsed, capped at 600 characters. In this tree's style the routine-description
  comment sits *between* the parameter list and the body, so that comment is included in the capture
  and may be truncated by the cap.
- **Implementation** — deliberately not filled in. The generator does not infer behaviour.
- **Variants** — how many extracted definitions share the name, and how many distinct SHA-256 body
  hashes they have.
- **Test evidence** — up to 20 links to call expressions in test-named files, with the true total
  when it exceeds the links shown.

## Test detection is path-based

```python
TEST_PATH = re.compile(r'(^|[/_.-])(tests?|testing|unittests?|testcases?)([/_.-]|$)', re.I)
```

A file counts as a test if a **path segment** matches. Consequences, verified against that
expression:

| Path | Detected? | Reality |
| --- | --- | --- |
| `base/tests/test_foo.cpp` | Yes | A test |
| `base/foo_test.py` | Yes | A test |
| `base/latest/foo.cpp` | No | `latest` is not `test` — correct |
| `base/ntos/se/utaccess.c` | **No** | It *is* a kernel unit test |
| `com/rpc/locator/drt/c/*.c` | **No** | It *is* a DRT test |

So `No matching call found in test-named files.` describes the index's detection rule, not the code.
See [Tests, diagnostics and debugging](/testing-debugging) for the conventions the rule misses.

Test matching is also by **unqualified leaf name**: `Obj::Method` is compared as `Method`, so a
matching call may belong to a completely unrelated function with the same name.

## Frequently asked questions

### Q: Why does my function not appear in the index at all?

Several possible reasons, all structural rather than judgemental:

```python
# unsupported extension
EXTENSIONS.get(Path('driver.asm').suffix.lower())          # None -> skipped
# excluded to prevent self-indexing
path.startswith(('documentation/', 'agents/'))             # True -> skipped
# a declaration without a body is not a function_definition node
# a macro-generated function may not parse as one either
```

Check the [coverage report](/reference/coverage) first: if the file is listed there, it was attempted
and partly failed. If it is absent from both the index and the coverage report, it was never
eligible.

### Q: Can I use the index to find all callers of a function?

No. It records call expressions **only in test-named files**, and only those that parse. For real
callers use `rg` against the subtree:

```bash
rg -n '\bSepAccessCheck\b' base/ntos | head -20
```

The index answers "is this exercised by a test-named file", not "who calls this".

### Q: Two entries have the same name and the same body hash. Are they duplicates?

Identical hashes mean identical *body text*. That is strong evidence of a copy, but not of
duplication in the engineering sense: the same body compiled into two drivers, or under two
`#ifdef` branches, is intentional. Read both `sources` files before concluding anything.

### Q: Two entries have the same name and different hashes. Is one a bug?

Not necessarily. A hash is SHA-256 over the body bytes, so a comment change, a whitespace change or a
single renamed local produces a different hash while the behaviour is identical. The generator says
this in the entry itself:

```text
Different hashes indicate text differences, not necessarily different behavior.
```

### Q: Why are there so many pages for one tree?

Because a tree like `base` has tens of thousands of definitions, and one page per 300 entries keeps
each file openable. `base-0001.md`, `base-0002.md`, … are ordered by path and line, so a given
definition stays on the same page number until the tree changes above it.

### Q: How do I regenerate just the part I am working on?

`--prefix` limits the scan, and it is repeatable:

```sh
python3 documentation/scripts/generate.py --prefix base/ntos/ --output /tmp/gen
python3 documentation/scripts/generate.py \
    --prefix base/ntos/ --prefix drivers/storage/ --output /tmp/gen
```

Do **not** publish a prefix-limited run as the full reference — it silently omits every other tree.
`--revision` changes what the source links point at, and `--output` redirects the whole run:

```sh
python3 documentation/scripts/generate.py --revision $(git rev-parse HEAD) \
    --output documentation/site/docs/reference
```

### Q: Why do source links not show my local edits?

Because they are pinned to a revision — `GITHUB_SHA` in the Pages workflow, or `git rev-parse HEAD`
locally. An uncommitted change exists in your working tree but not at that commit, so the link shows
the older content. Commit first, or pass `--revision` explicitly.

### Q: How is this generator itself tested?

By `documentation/tests/test_generate.py`, which runs on any platform and is executed by the Pages
workflow before the site is built:

```sh
python3 -m unittest discover -s documentation/tests
```

The suite covers C and Python extraction, body-hash sensitivity, the test-path rule, test-evidence
rendering, stale-page cleanup, and the per-page FAQ — including that a backtick inside a captured
signature cannot terminate the fenced code block early.

### Q: What would make this index better, and what is deliberately left out?

Left out by design: preprocessing, symbol resolution, cross-language analysis, execution, and any
claim about what a function does. Adding them would turn a fast, deterministic, evidence-linked
inventory into an analysis whose failures are invisible. The honest improvement is to make the gaps
legible — which is what the per-page FAQ, the `Variants` wording and the coverage report are for.
