**Read this before running any historic build command.** This is a Windows `cmd` / NMAKE /
`build.exe` source tree — not CMake, not npm, not a Linux project. The repository README describes
the intended workflow; this page separates that workflow from what is actually checked in.

## The three files that define a component

Every buildable component is described by a `dirs` file (traversal), a `sources` file (target) and a
`makefile` (indirection to the shared rules).

A complete, real leaf component —
[`sdktools/gflags/sources`](https://github.com/havaianasdestruido/neo-nt5/blob/main/sdktools/gflags/sources):

```bat
TARGETNAME=gflags
TARGETPATH=obj
TARGETTYPE=PROGRAM

SOURCES=gflags.cxx gflags.rc

UMTYPE=console

USE_MSVCRT=1
USE_NATIVE_EH=1

!if $(IA64)
LINKER_STACKSIZE=-stack:0x100000,0x6000
!else
LINKER_STACKSIZE=-stack:0x100000,0x3000
!endif

TARGETLIBS=$(SDK_LIB_PATH)\ntdll.lib    \
           $(SDK_LIB_PATH)\user32.lib

NTTARGETFILES=$(O)\gflags.res
```

Its entire `makefile` is a single include, and says so itself:

```bat
REM DO NOT EDIT THIS FILE!!!  Edit .\sources. if you want to add a new source
REM file to this component.  This file merely indirects to the real make file
REM that is shared by all the components of NT OS/2
!INCLUDE $(NTMAKEENV)\makefile.def
```

So **add source files to `sources`, never to the local `makefile`.** The shared rules live in
[`tools/makefile.def`](https://github.com/havaianasdestruido/neo-nt5/blob/main/tools/makefile.def),
whose own header documents the contract: the developer supplies `sources` with the required
`TARGETNAME`, `TARGETPATH`, `TARGETTYPE` and `SOURCES`; `build.exe` generates
`$(_OBJ_DIR)\_objects.mac` from it.

### TARGETTYPE values

`TARGETTYPE` decides what kind of artifact the node produces. Values used in this tree include:

| Value | Artifact | Example from the tree |
| --- | --- | --- |
| `PROGRAM` | Executable | `sdktools/gflags` |
| `DYNLINK` | DLL | `net/ndis`-adjacent user-mode components |
| `LIBRARY` | Static library | `base/ntos/io/iomgr` |
| `DRIVER` | Kernel-mode driver | `drivers/storage/disk` |
| `MINIPORT` | NDIS miniport | drivers under `drivers/net` |
| `HAL` | Hardware abstraction layer | `base/hals` |
| `GDI_DRIVER` | Display driver | `drivers/video` |
| `NOTARGET` | No linked binary at this node | header/fragment-only nodes |

A kernel static library, from
[`base/ntos/io/iomgr/sources.inc`](https://github.com/havaianasdestruido/neo-nt5/blob/main/base/ntos/io/iomgr/sources.inc):

```bat
MAJORCOMP=ntos
MINORCOMP=io

TARGETNAME=iomgr
TARGETTYPE=LIBRARY
TARGETPATH=obj

INCLUDES=..;..\..;\
         ..\..\..\inc;\
         $(DDK_INC_PATH);\
         $(NET_INC_PATH);\
         $(SDKTOOLS_INC_PATH);\
         $(HALKIT_INC_PATH)
```

Note `sources.inc` rather than `sources`: the file is *included* by the architecture-specific nodes
(`up/sources`, `mp/sources`) instead of being a leaf itself. Do not infer a target's extension from
`TARGETTYPE` alone — consult `tools/makefile.def`.

### Path macros

Shared include and library roots are defined once in
[`tools/projects.inc`](https://github.com/havaianasdestruido/neo-nt5/blob/main/tools/projects.inc),
one triplet per engineering tree:

```bat
BASE_INC_PATH=$(PUBLIC_INTERNAL_PATH)\Base\inc
BASE_LIB_DEST=$(PUBLIC_INTERNAL_PATH)\Base\lib
BASE_LIB_PATH=$(BASE_LIB_DEST)\$(TARGET_DIRECTORY)
```

That is why a `sources` file can write `$(BASE_LIB_PATH)\foo.lib` without knowing where the build
output went. `TARGET_DIRECTORY` carries the architecture and build type.

## Razzle

[`tools/razzle.cmd`](https://github.com/havaianasdestruido/neo-nt5/blob/main/tools/razzle.cmd)
establishes the build environment for a `cmd` session. It derives the source root from its own
location, which is why it must be invoked by path:

```bat
set RazzleToolPath=%~dp0
if "%RazzleToolPath:~-1%" == "\" set RazzleToolPath=%RazzleToolPath:~0,-1%
set _NTROOT=%_nttemproot%
```

Environment it sets (line numbers in the checked-in script):

| Variable | Set at | Meaning |
| --- | --- | --- |
| `BUILD_OFFLINE` | 206 | `offline` argument; do not reach build-lab services |
| `BUILD_DEFAULT_TARGETS` | 318 | `-%_BuildArch%` — default architecture for `build` |
| `BUILD_CHECKED_KERNEL` | 391 | `1` when the checked-kernel switch is given |
| `_NTTREE` | 443 | Output tree: `%BinariesDir%%_ArgSepChar%%_BuildArch%%_ArgEmulDir%%_BuildType%` |

### The `ChkKernel` spelling problem

Three different spellings of the same switch appear in this repository. Only one is parsed. The
argument loop at line 96:

```bat
if /I "%1" == "ChkKernel" set _ArgChkKrnl=true&goto ArgOK
```

and its effect at line 391:

```bat
if "%_ArgChkKrnl%" == "true" set BUILD_CHECKED_KERNEL=1&& set _KernelType=/ChkKernel
```

- `razzle.cmd` parses **`ChkKernel`** (comparison is case-insensitive via `/I`).
- `razzle.cmd`'s own `:usage` text prints **`chkkernel`** — works, because of `/I`.
- The root `README.md` prints **`CkhKernel`** — a transposition that silently does nothing.

An unrecognised argument is not an error in this script; it is ignored. Consult the script, not the
README, for switch spellings.

## Version and build-number targets

The root [`makefil0`](https://github.com/havaianasdestruido/neo-nt5/blob/main/makefil0) is an NMAKE
file, not a Razzle script:

```bat
!INCLUDE $(NTMAKEENV)\makefile.plt

all: echobldmsg

cleanup: nuke_binaries

clean: cleanup set_builddate set_buildnum DelPub all

set_builddate:
!if !defined(BUILD_DATE_SET) || !exists($(BASEDIR)\__blddate__)
    @perl $(RAZZLETOOLPATH)\updtnum.pl
!endif
    @echo BuildDate:
    @type $(BASEDIR)\__blddate__
    binplace $(BASEDIR)\__blddate__

set_buildnum:
    @perl $(RAZZLETOOLPATH)\genbldno.pl
```

So the README's `nmake set_builddate set_buildnum set_buildname -f makefil0` works through these
targets, and the generated stamp files are `__blddate__`, `__bldnum__` and `__qfenum__` at the source
root. Product version macros are separate, in
[`public/sdk/inc/ntverp.h`](https://github.com/havaianasdestruido/neo-nt5/blob/main/public/sdk/inc/ntverp.h).

## Postbuild and staging

`tools/postbuild.cmd` drives the data file
[`tools/postbuildscripts/pbuild.dat`](https://github.com/havaianasdestruido/neo-nt5/blob/main/tools/postbuildscripts/pbuild.dat).
It is a sequence of script invocations with `BEGIN` / `END` barrier pairs and run-mode tags:

```bat
BEGIN %RazzleToolPath%\PostBuildScripts\SwapInOriginalFiles.cmd
END %RazzleToolPath%\PostBuildScripts\SwapInOriginalFiles.cmd
BEGIN %RazzleToolPath%\PostBuildScripts\Aggregation.cmd
END %RazzleToolPath%\PostBuildScripts\Aggregation.cmd
FULL %RazzleToolPath%\PostBuildScripts\layout.cmd
END %RazzleToolPath%\PostBuildScripts\layout.cmd
INCREMENTAL %RazzleToolPath%\PostBuildScripts\BinDiff.pl
END %RazzleToolPath%\PostBuildScripts\BinDiff.pl
OFFICIAL %RazzleToolPath%\PostBuildScripts\capturesourcefilelist.cmd -g ntdev
BEGIN %RazzleToolPath%\PostBuildScripts\timebomb.cmd
```

The checked-in `pbuild.dat` contains 58 `BEGIN` lines, 75 `END` lines, and 4 `INCREMENTAL`,
7 `OFFICIAL`, 2 `COVERAGE` and 1 `FULL` tagged lines. A `BEGIN` starts a step whose `END` must
complete before later steps run; a mode tag restricts a step to a kind of build run.

### The timebomb

`timebomb.cmd` is bracketed at `pbuild.dat` lines 33 and 110, and its own line 44 sets the interval:

```bat
if /i not "%lang%"=="usa" (
   call logmsg.cmd "%script_name% does not apply to international builds."
   goto :EOF
)

set DAYS=180
if "%DAYS%" == "0" goto :EOF
```

It then swaps timebomb versions of `setupreg.hiv` and the product ID across
`. perinf srvinf blainf sbsinf entinf dtcinf`. `DAYS=0` disables it. It applies only to `usa`
builds.

The README's SKU codes (`srv`, `sbs`, `ads`, `dtc`, `bla`, `per`, `pro`) describe intent. They are
not evidence that an image for each SKU can be produced from this checkout.

## Frequently asked questions

### Q: What is the smallest thing I can build to check a change?

Enter a fresh Razzle session, `cd` to the component, and run `build` there — but only after its
published dependencies exist, because `TARGETLIBS` resolves against
`$(PUBLIC_INTERNAL_PATH)` import libraries:

```bat
C:\Windows\system32\cmd.exe /k C:\NT\tools\razzle.cmd free offline
cd C:\NT\drivers\storage\disk
build
```

`drivers/storage/disk/sources` is a good example of the dependency problem:

```bat
TARGETNAME=disk
TARGETPATH=obj
TARGETTYPE=DRIVER

TARGETLIBS=$(DDK_LIB_PATH)\classpnp.lib
```

If `classpnp.lib` has not been built and published, that target cannot link — no amount of local
source correctness fixes it. Report the missing prerequisite instead of working around it.

### Q: `build /cZP` or `build /ZP`?

Both are README commands, and the difference is `/c`:

```bat
build /cZP     rem clean rebuild of everything the traversal reaches
build /ZP      rem incremental: only what changed since the last clean build
```

`/Z` is parallel traversal, `/P` is the "prompt on error" behaviour of the historical `build.exe`.
Do not assume either flag compiles an arbitrary isolated directory — reachability comes from the
`dirs` chain, and the flags do not add directories to it.

### Q: Where does output go, and can I redirect it?

To `_NTTREE`, computed at `razzle.cmd` line 443 as
`%BinariesDir%%_ArgSepChar%%_BuildArch%%_ArgEmulDir%%_BuildType%`. With defaults that is
`binaries.x86free` style output under the source root. `binaries_dir <basepath>` overrides the base
path and `sepchar` overrides the `.` separator — useful for putting several architectures under one
parent directory with `\`. Object directories and staged binaries are **generated**, not source;
never commit them.

### Q: Why did `filechk` fail after postbuild?

Because the README's optional `tools\missing.cmd` step was skipped and that script is not in this
checkout at all. The README says: "Expect `filechk` errors if you skip the optional `missing.cmd`
step." Here it cannot be performed — so a `filechk` failure in this tree is expected, not a defect in
your change. Say so plainly rather than silencing the check.

### Q: How do I change what ships for one SKU? {#sku-shipping}

Through setup metadata and postbuild selection, not through the C source that already compiles. The
chain is: `sources` target → published binary via `binplace` → setup INF or registration →
`pbuild.dat` filtering → SKU media. Relevant locations include
[`base/ntsetup/inf`](https://github.com/havaianasdestruido/neo-nt5/tree/main/base/ntsetup/inf),
`mergedcomponents/setupinfs`, per-project `setup`/`sld` folders, and the SKU loops in scripts such as
`timebomb.cmd` (`. perinf srvinf blainf sbsinf entinf dtcinf`). A source fix is not a delivered fix
until the target is reachable, packaged and installed for the intended architecture, locale and SKU.

### Q: My `sources` file is ignored. What did I miss?

Three common causes, all checkable without a build:

```bash
# 1. Is the directory actually in an ancestor dirs file?
grep -rn "$(basename $PWD)" ../*/dirs ../dirs dirs 2>/dev/null

# 2. Is it OPTIONAL_DIRS, or behind an architecture qualifier like foo{ia64,x86}?
grep -n "OPTIONAL_DIRS\|{.*}" ../dirs

# 3. Is it a leaf at all? NOTARGET nodes and *.inc fragments produce no binary.
grep -n "TARGETTYPE\|TARGETNAME" sources sources.inc 2>/dev/null
```

A file being present in Git does not make it a root build target.

### Q: Can I run any of this on Linux?

The build itself, no — it needs `cmd`, NMAKE and the historical `build.exe`. The *documentation and
inventory* tooling in this repository is Python and runs anywhere:

```sh
python3 agents/generate_catalog.py --check   # catalog matches the tracked tree
python3 agents/verify.py                     # Markdown links + guide coverage
python3 -m unittest discover -s documentation/tests
git diff --check                             # whitespace defects
```
