# NEONT 5 daily-driver roadmap

**Authority:** project-wide implementation checklist. **Baseline:** commit `c24c9fcb83ef2ae3d7c600a4aff557db75e5732b`, inspected 2026-10-31. This is a plan, not a claim that an OS image can currently be built, booted, distributed, or used safely on the Internet. No roadmap implementation is included in this document.

## How to use and maintain this plan

- Status: `[ ]` not completed (including work that has not been tested); `[x]` completed **only to the stated scope**, with evidence; `[!]` blocked or infeasible under the stated conditions. P0 = prerequisite/release safety; P1 = first supported daily-driver baseline; P2 = expanded coverage; P3 = optional/long-horizon. IDs are stable. Each checkbox is a separately trackable work item; the subtasks after it and the section exit criteria are part of its definition of done.
- Sections correspond to phases, not a promise of calendar dates. A task may start earlier after its dependencies are met; do not close a gate on implementation alone. Quick wins are marked **QW**; **ARCH** means a multi-component architectural project, not a header-only backport.
- For every completed item record commit/PR, owner, date, exact commands, configuration, results, artifacts and unresolved risks in the tracker or immediately beneath the item. Retain an item and its history if scope changes; add IDs for newly found work and link related items. Reopen on regression. Recheck claims against the current tree and rerun the relevant tests; an old report is not a current status.
- Gate metrics below are proposed acceptance thresholds, not measured baselines. Specify hardware, image hash, architecture, SKU, locale, workload and test duration with every result. If a threshold cannot be met, record a blocker and do not claim the gate passed.
- For every implementation: trace source owner → `dirs`/`sources` → public/published ABI → setup/INF/registration → postbuild/SKU → runtime tests; include checked/free and supported architecture paths. Do not edit generated/published copies alone. Follow `AGENTS.md`, with project approval for necessary policy changes. Protect private keys, product keys, copyrighted media, test credentials and user data from logs and artifacts.

## Product scope and hard constraints

The intended first target is a **proposed**, not yet proven, x86 VM baseline; investigate AMD64 as the preferred long-term native desktop in Phase 1. Decide one SKU, language and supported host/hardware matrix before promising compatibility. Phase 1 is a lab-only milestone; a modern daily-driver release requires the security, update, app and acceptance gates below. Legacy NT compatibility and contemporary security have unavoidable trade-offs.

- [!] **P0 GOV-01 — Rights and provenance gate:** `README.md` describes proprietary Microsoft-derived material; no root license grant was identified in the shallow license inventory. Obtain qualified legal review and documented rights to possess, modify, build and distribute source, binaries, SDK, media, fonts, codecs, firmware, signing material and third-party dependencies in every target jurisdiction. **Unblock:** written rights and component-level provenance/SBOM; otherwise do not publish artifacts or integrate external code.
- [!] **P0 GOV-02 — No implicit OneCore license or source:** “OneCore” is Microsoft's modern shared Windows platform, not a drop-in DLL or automatically redistributable layer. Native integration of Microsoft implementation, SDK binary, headers, API-set schema or third-party compatibility projects requires explicit rights, version and license compatibility. **Unblock:** legal approval plus a named, supportable source/implementation; absent that, implement independently from public contracts or use a separately licensed compatible project after review. Do not copy leaked/proprietary code or bypass activation/DRM.
- [!] **P1 GOV-03 — No promise of Windows 10/11 equivalence:** modern driver frameworks, WDDM/DXGI/D3D, UWP/WinRT services, isolation, code integrity, security hardware, app stores and modern vendor installers rely on entire kernel, service and policy ecosystems. API names/version spoofing cannot supply them. **Unblock each claim:** architectural design, lawful implementation, target-specific tests and vendor support; otherwise list as unsupported.
- [!] **P1 GOV-04 — Hardware and trust anchors are external:** drivers require device specifications/firmware and redistribution permission; production signing keys, trusted UEFI signing arrangements, update trust anchors and vendor certificates cannot be assumed. **Unblock:** approved designs, access and agreements; never use checked-in test keys as production trust. Some devices will remain unsupported.
- [ ] **P0 GOV-05 — Publish a threat model and support policy:** enumerate remote/local/physical adversaries, admin vs standard user, malicious documents/drivers, network exposure and supported firmware/VMs; explicitly warn that early builds are isolated-lab only. Exit: approved scope, exclusions, response owners and an Internet-use go/no-go checklist.
- [ ] **P0 GOV-06 — Resolve exposed credentials and signing material:** review `README.md` product keys, `tools/driver.pvk`, `tools/testroot.cer`, `tools/testpca.cer` and test key material in `ds/security/cryptoapi/test` without reproducing values. Determine ownership/validity and exposure, revoke/rotate where applicable, restrict distribution and coordinate history cleanup with maintainers/legal; use secret scanning and a nonsecret fixture allowlist. Exit: documented disposition for each class, no production reliance on historical keys, CI blocks new secrets.
- [ ] **P1 GOV-07 — Set support horizon and funding:** assign maintainers for kernel, hardware, security, releases and dependencies; define supported branches, response SLA, upstream monitoring and end-of-support procedure. Exit: named owners, on-call process and published lifecycle before public beta.

## Phase 2 — Security and network baseline

**Dependencies:** Phase 1 working system and recovery; GOV-01/04/05/06; verified trust bootstrap before online update. **Gate:** threat-model review, no known release-blocking vulnerabilities, and all security and transport tests below pass. Do not market a patched legacy kernel as equivalent to current Windows security.

### Security foundations and exposure

- [ ] **P0 SEC-01 — Attack surface inventory:** map installed services, listeners, RPC endpoints, COM activation, browser controls, drivers, accounts and privileges across `ds/security`, `base/screg`, `net`, `inetsrv`, `termsrv`, `printscan`; determine actual SKU defaults. Exit: baseline port/service scan and dependency table; disable unnecessary server roles, legacy protocols and anonymous interfaces by default.
- [ ] **P0 SEC-02 — Security servicing backlog:** map applicable publicly documented vulnerabilities and advisories to exact code/version, not only product names; assess exploitability, source differences, patch rights and regression risk. Exit: all release-blocking items fixed/tested or functionality disabled, with signed-off exceptions and disclosure policy.
- [ ] **P1 SEC-03 — Boundaries and least privilege:** audit token creation, impersonation/revert, object ACL inheritance, default DACLs, privilege checks, service accounts, sessions and named-pipe/RPC access across `base/ntos/{se,ob}`, `ds/security/base/lsa` and SCM. Exit: standard-user negative tests cannot write system paths, access other users' secrets or invoke privileged operations; expected authorized operations still work.
- [ ] **P1 SEC-04 — Memory-safety hardening:** enable supported compiler stack cookies, warnings, safe string and integer handling; audit parsers and network/kernel buffers with static analysis, fuzzing and fault injection. Exit: all externally reachable prioritized parsers have fuzz harnesses and regression corpus; zero unresolved critical/high findings for release scope.
- [ ] **P1 SEC-05 — NX/DEP and ASLR feasibility (ARCH):** audit hardware NX, page tables, PAE/AMD64, image relocation, loader entropy, shared mappings and legacy driver compatibility; implement only verifiable policies and opt-outs. Exit: execution from non-executable test pages fails, per-boot/process address distributions measured, compatibility exceptions visible; no claim of full modern ASLR based on image flags alone.
- [ ] **P2 SEC-06 — Further exploit mitigations (ARCH):** evaluate CFG-like indirect-call checks, high-entropy ASLR, kernel pool hardening, SMEP/SMAP, secure exception handling and modern compiler/runtime requirements per CPU/architecture. - [!] **P2 SEC-07 — Strong isolation features:** modern VBS/HVCI, protected processes, AppContainer, full modern UAC and equivalent secure-boot chain require broad kernel, hypervisor, identity, driver and platform redesign, not API shims. **Unblock:** funded architecture, hardware/firmware trust and compatibility design with end-to-end independent security review; otherwise advertise none of these protections.
- [ ] **P1 SEC-08 — Authentication and credential storage:** audit GINA/LSA, SAM, Kerberos, NTLM and secret storage; disable weak/obsolete authentication by default where compatible, limit credential exposure and provide explicit migration/lockout recovery. Exit: standard-user/admin separation, password change, domain/local login where supported, downgrade and replay tests pass without logging credentials.
- [ ] **P2 SEC-09 — Modern identity integration:** assess FIDO2/WebAuthn, MFA and federated OAuth/OIDC clients as separate components; define secure browser/cryptographic and authenticator dependencies, recovery and offline behavior. Exit: approved threat model and interoperable end-to-end tests before advertising any mechanism; no substitution of insecure credential prompts.
- [ ] **P1 SEC-10 — Audit, telemetry and privacy:** provide tamper-aware security events, crash reporting opt-in, redaction, retention and offline operation; restrict logs/dumps. Exit: authentication and update failure events are actionable; tests confirm secrets and user content are not uploaded by default.

## Phase 4 — Modern API and application compatibility

**Dependencies:** Phase 1 loader/kernel, Phase 2 security/crypto, Phase 3 relevant device stacks. **Gate:** measured compatibility with specifically named versions/workflows, not a blanket claim of modern Windows compatibility. Track legal permission separately for each runtime/app.

### ABI, APIs and shims

- [ ] **P0 API-01 — Create compatibility inventory:** select candidate apps/libraries; record PE architecture, subsystem/version, static/delay imports by DLL/name/ordinal, dynamic `GetProcAddress`, COM classes, registry/service/driver dependencies, CPU instructions and licensing. Compare with actual exports/build targets. Exit: reproducible per-app missing-contract report and ranked dependency graph; imports alone do not imply runtime success.
- [ ] **P1 API-02 — Define OneCore-compatible surface (ARCH):** map relevant documented Win32 API contracts and API-set names to owners in `base/win32/client`, `base/ntdll`, `windows/core`, `com` and published SDK; distinguish documented behavior from internal/undocumented implementation. Decide independently implemented native exports vs app-local redirection after GOV-02. Exit: reviewed versioned API matrix, semantic tests and source provenance; no implied Microsoft OneCore binary integration.
- [ ] **P1 API-03 — Loader/API-set resolution (ARCH):** analyze `base/ntdll/{ldrinit,ldrsnap,ldrutil}.c`, activation contexts and PE imports; design schema/forwarder resolution, DLL search order, ordinals, delay loads, SxS, recursion/cycle limits and trusted paths for chosen targets. Exit: x86 and selected x64 loader fixtures pass including missing modules, malicious path injection, recursive forwarders and exact error behavior.
- [ ] **P1 API-04 — Backport selected user-mode APIs:** prioritize actual inventory gaps in synchronization, threads, file I/O, time, locale, process, environment and error APIs; specify calling convention, structures, ownership, errors, reentrancy and cancellation. Exit: each added function has ABI/export checks, native-reference differential tests where lawful, concurrency/invalid-input tests and documented limitations.
- [ ] **P1 API-05 — Kernel-backed contracts:** for APIs requiring new syscalls, object types or scheduler/memory behavior, version native/Win32 interfaces across `base/ntos`, `base/ntdll` and `public` headers, including WOW64 translation. Exit: old binaries keep behavior, new ABI passes 32/64-bit layout and privilege tests; unsupported semantic cases return documented errors rather than fake success.
- [ ] **P1 API-06 — App-specific shims:** use `windows/appcompat/{shimengines,shims,db}` only for scoped, versioned behavior; implement version lies and workarounds per executable with safe opt-out and logging. Exit: each shim has before/after reproducible test, negative tests for unrelated apps, manifest provenance and removal condition.
- [ ] **P1 API-07 — COM/RPC and SxS:** review `com/{ole32,rpc}`, IDL, marshaling, activation, security descriptors, apartment/threading, manifests and assembly binding. Exit: tested clients and servers work across processes, malformed marshaled data rejected, old registration/SxS binaries unaffected.
- [ ] **P2 API-08 — CRT/C++ and runtime libraries:** audit `base/crts`, public libraries and compiler ABI; support target runtimes, exception unwinding, TLS, atomics, thread-safe initialization, allocator ownership and side-by-side deployment. Exit: selected official compatibility test suite plus cross-DLL allocation/exception tests pass per architecture.
- [ ] **P2 API-09 — WOW64 and architecture limits (ARCH):** verify syscall/handle/pointer conversion, registry/filesystem redirection, callbacks, exception unwinding and driver boundaries in `base/wow64` and `windows/core/wow64win`; test only after a proven 64-bit baseline. Exit: selected 32-bit applications pass on 64-bit image without kernel-driver cross-architecture loading claims.
- [ ] **P2 API-10 — Modern app models:** inventory WinRT activation, packaged/MSIX apps, services, broker/security and graphics requirements; prototype only components needed by selected workloads. Exit: published per-API support and end-to-end tests, or explicit unsupported decision with dependencies; no pretend-success stubs.

### Real applications and libraries

- [ ] **P1 APP-01 — Publish test matrix:** choose legally obtainable, maintained versions of a browser, text editor, archive manager, PDF viewer, office suite, media player, terminal, compiler, debugger and a representative game. Specify CPU, GPU, installer, update channel and support lifespan. Exit: each row records install, launch, essential workflow, security, failures, regression ID and reproducible artifacts.

- [ ] **P1 APP-03 — Developer tools and runtimes:** test chosen C/C++ compiler/linker, Git client, scripting runtime, package tooling, TLS/downloads, Unicode paths and process spawning; add required SDK exports/headers. Exit: build, test and debug a nontrivial sample entirely on the OS with pinned versions and no insecure dependency transport.
- [ ] **P1 APP-04 — Productivity and communication:** exercise document edit/save/reopen, PDF viewing, mail/calendar or secure web alternative, file transfer and printing with selected apps. Exit: documented 30-minute user scenario, no data corruption, successful recovery after crash, current transport security.
- [ ] **P2 APP-05 — Multimedia applications:** test chosen media editor/player, device access, codec/container edge cases, capture permissions and hardware acceleration fallback. - [ ] **P2 APP-06 — Games:** inventory DirectInput/DirectSound/DirectDraw/D3D/OpenGL versions, audio, controllers, networking, launchers and anti-cheat kernel drivers. ## Reference points and dependency order

1. **Legal/provenance + threat model → build graph/toolchain → verified build → isolated boot/recovery.** An inaccessible or unlicensed input is a blocker, not an invitation to redistribute it.
2. **Kernel/PnP/storage → hardware drivers → daily workflows.** A driver binary built for a later WDM/KMDF/NDIS/WDDM contract is not automatically compatible; adding import stubs cannot reproduce required IRQL, memory, power or ABI semantics.
3. **Entropy/crypto/PKI + networking → authenticated updates → connected apps.** TLS alone does not secure an unpatched browser/kernel; browser sandboxing and an ongoing security-response process are separate release gates.
4. **Application import/behavior inventory → loader + APIs → scoped shims → runtime/application tests.** Build SDK, publication, installation and WOW64 alongside implementations; avoid version spoofing as a substitute for semantics.
